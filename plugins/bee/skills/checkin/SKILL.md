The steps below are the bee server's `checkin` prompt (`/mcp__plugin_bee_bee__checkin`). The task
in step 1 is what followed `/bee:checkin`, or `$bee:checkin` in Codex. Codex fills nothing into
step 1's quotes, so there, take the task from the person's message. If nothing followed, it is the
task you are on in this conversation. With none yet, it is "waiting for a task": ask on the card
what to work on, wait for the answer as in step 5, then do it.

Check in on the bee board: one status card for this session, kept current while you work, so the person sees from one page what each of their sessions is doing and answers what you need from them. The bee server's instructions say how to take part; follow them.

Everything on the card is visible to anyone attached, over plain HTTP. Write short summaries only: never a secret, token, key, password or environment value, and no file contents beyond a one-line summary. Name a file; don't paste it.

1. Name the card. The repo is the directory that holds this repository's shared .git: run `git rev-parse --path-format=absolute --git-common-dir` and take the name of the directory above `.git`, so a worktree uses its repository's name; outside git, use the working directory's name. The surfaceId is that name in lower case, each character other than a-z, 0-9 and - turned into -, as "fireworks-compose". Call bee_board: if it lists that id, open or closed, take the first of <id>-2, <id>-3, … it doesn't list. Keep that id for the whole session. The title is "<repo> — <task>", the task in one line: the task is what the person typed after the command: "$ARGUMENTS", though that may be only its first word, so take the whole of what they typed.
2. Open the card with bee_surface_open, that surfaceId and title, these components and data, your own words in place of the example's:
  components: [{"id":"root","component":"Column","children":["now","progress","decision","stop"]},{"id":"now","component":"Text","text":{"path":"/now"}},{"id":"progress","component":"Text","text":{"path":"/progress"}},{"id":"decision","component":"Column","children":["ask","options","answer","send"]},{"id":"ask","component":"Text","variant":"h5","text":"Squash the fix into one commit?"},{"id":"options","component":"Row","children":["opt-1","opt-2"]},{"id":"opt-1","component":"Button","child":"opt-1-label","action":{"event":{"name":"decide","context":{"choice":"squash"}}}},{"id":"opt-1-label","component":"Text","text":"Squash"},{"id":"opt-2","component":"Button","child":"opt-2-label","action":{"event":{"name":"decide","context":{"choice":"keep"}}}},{"id":"opt-2-label","component":"Text","text":"Keep the commits"},{"id":"answer","component":"TextField","label":"Or say something else","value":{"path":"/answer"}},{"id":"send","component":"Button","child":"send-label","action":{"event":{"name":"answer","context":{"text":{"path":"/answer"}}}}},{"id":"send-label","component":"Text","text":"Send"},{"id":"stop","component":"Row","children":["done","pause"]},{"id":"done","component":"Button","child":"done-label","action":{"event":{"name":"done","context":{}}}},{"id":"done-label","component":"Text","text":"Done"},{"id":"pause","component":"Button","child":"pause-label","action":{"event":{"name":"pause","context":{}}}},{"id":"pause-label","component":"Text","text":"Pause"}]
  data: {"now":"Fixing the flaky retry test","progress":"- done: found the race in RetryPolicy\n- next: fix it, run the suite","answer":""}
  now is what you are doing, in one line. progress is a short list: "- done: …" lines, then "- next: …" lines. decision holds what you need from the person: ask says it in one line, and options holds a Button per option, each recording "decide" with {choice}. For an open question keep answer and send, which record "answer" with {text}; when the options cover it, drop them from decision's children. With nothing to ask, decision's children are []. Done and Pause always stay.
3. Set bee_presence to "<repo>: <now>", then go on with your real work in the repo.
4. At each natural checkpoint (a step finished, a test run, before a commit), bee_surface_update the same card, never a new surface: data {"/now": …, "/progress": …}, and components only when the decision changes. Update bee_presence to match. Then glance for a click: bee_wait_action with your surfaceId and timeoutSeconds 1, passing back the cursor it returned last time, and handle any record as in steps 5 and 6.
5. When you need a decision, ask it on the card: upsert ask and options, and set decision's children. Then loop bee_wait_action with your surfaceId and timeoutSeconds 20, passing back the cursor each call; timedOut only means call again. Act on the record: "decide" carries {choice}, "answer" carries {text}. bee_action_done it with its recordId and token, set decision's children to [], note the outcome in progress, and carry on. Don't hold a wait for a decision you don't need yet: ask, keep working, and pick the answer up at a checkpoint.
6. A "done" or "pause" record ends the check-ins: bee_action_done it, write one line into now saying what you finished and what is left, set decision's children to [], clear your bee_presence status, and say here that you have stopped checking in. Leave the card open and stop writing to it.
